# BOOK-LIBRARY и Quartz

Интеграция BOOK-LIBRARY с Quartz нужна не для того, чтобы превратить сайт в зеркало файлового каталога. Quartz остаётся сайтом заметок, проектных страниц и подборок. BOOK-LIBRARY остаётся системой, где хранятся книги, обложки, категории, переводы, админские задачи и временные ссылки на скачивание.

Такое разделение важно. Если просто скопировать книги в статический сайт, быстро появляются проблемы: где обновлять метаданные, как отзывать файл, что делать с обложками, как не публиковать черновые переводы, как не смешивать заметки с файловым архивом. Поэтому интеграция сделана аккуратнее.

## Что уже есть на стороне Quartz

В Quartz уже есть несколько частей, связанных с библиотекой:

- страница `content/library.md`;
- компонент `quartz/components/LibraryPage.tsx`;
- конфиг `quartz/static/data/bookshelf.json`;
- generated catalog `quartz/static/generated/bookshelf-catalog.json`;
- mirrored covers через `quartz/util/bookshelfCatalog.ts`.

Эти элементы дают сайту статическое представление библиотеки: можно показать отобранный каталог и обложки без превращения Quartz в backend для книг.

## Public API вместо прямого доступа к файлам

BOOK-LIBRARY отдаёт публичные данные через public API. Это правильная граница для Quartz: сайт может получить карточки, категории и обложки, но не должен знать внутреннее устройство uploads или SQLite.

Файлы книг остаются за backend. Скачивание проходит через temp-token flow: сначала запрашивается временная ссылка, потом backend отдаёт файл по token. Это сохраняет контроль на стороне библиотеки и не раскрывает постоянные URL на книги.

Quartz в этой схеме не становится посредником скачивания. Он может быть витриной и контекстом, но не файловым сервером.

## CORS, CORP и public origins

Для такой интеграции важны не только данные, но и браузерные границы. В BOOK-LIBRARY разделены public и admin origins. Публичная часть может быть доступна Quartz-сайту, а админские API не должны случайно открываться тем же способом.

Для обложек используется public CORP. Это помогает корректно показывать изображения в публичных контекстах и не смешивать правила доступа к covers с правилами доступа к admin API.

Здесь нет цели сделать сложную security-схему ради самой схемы. Смысл проще: Quartz получает только то, что должно быть публичным, а операции управления остаются в React-админке BOOK-LIBRARY.

## Static generated catalog

Quartz — статический сайт, поэтому ему удобнее работать с generated catalog. Вместо того чтобы каждый посетитель сайта ходил в живой backend BOOK-LIBRARY, часть данных можно подготовить заранее и положить в статический JSON.

Такой подход даёт несколько плюсов:

- сайт остаётся быстрым и статическим;
- сборка контролирует, какие книги попадают в публичное представление;
- можно использовать mirrored covers;
- нет зависимости от постоянной доступности backend для каждого просмотра страницы;
- проще делать curated-подборки.

При этом generated catalog не должен становиться единственным источником истины. Источник истины остаётся в BOOK-LIBRARY: SQLite, uploads, админка и pipeline импорта.

## Mirrored covers

Обложки можно зеркалировать в Quartz как статические файлы. Это удобно для карточек: сайт не зависит от внешних URL обложек и может показывать изображения рядом с заметками.

Но mirrored covers — это не перенос всей библиотеки. Обложка нужна для публичной карточки, а файл книги остаётся в BOOK-LIBRARY. Такое разделение хорошо ложится на формат сайта: Quartz показывает контекст, BOOK-LIBRARY обслуживает библиотечные операции.

## Чем это отличается от прямой публикации книг

Прямая публикация книг на Quartz выглядела бы проще технически: положить файлы в static-директорию и дать ссылки. Но для этого проекта такой вариант хуже.

Он ломает несколько важных границ:

- скачивание перестаёт идти через временные токены;
- сложнее скрывать черновые или снятые с публикации переводы;
- Quartz-репозиторий начинает разрастаться файлами книг;
- админка теряет контроль над тем, что реально доступно читателю;
- становится труднее поддерживать одну версию карточки и обложки.

Поэтому Quartz лучше использовать как витрину и навигационный слой. А сами файлы, import jobs, translation jobs и публикация artifacts должны оставаться в BOOK-LIBRARY.

## Curated-подборки вместо полного зеркала

Самый полезный следующий шаг — не показывать весь каталог подряд, а делать curated-подборки. Например: книги по теме проекта, подборка по разработке, художественная полка, книги рядом с конкретной заметкой.

Такой формат хорошо подходит Quartz. Статический сайт силён не тем, что хранит всё, а тем, что связывает материалы между собой. Подборка может содержать короткий комментарий, ссылку на заметку, обложку, автора и путь к карточке книги.

## Markdown-карточки и обратные ссылки

Для отдельных книг можно генерировать Markdown-карточки. Не обязательно для всей библиотеки — только для тех записей, которые действительно нужны на сайте.

Возможная карточка может содержать:

- название и автора;
- категорию или подборку;
- короткое описание;
- обложку;
- связь с заметками на сайте;
- ссылку на карточку или скачивание через BOOK-LIBRARY.

Интереснее всего здесь обратные ссылки. Если по книге есть заметка, обзор или конспект, Quartz может вести к книге, а BOOK-LIBRARY — обратно к заметке. Тогда библиотека становится не отдельным складом файлов, а частью личной базы знаний.

## Где проходит граница

Граница выглядит так:

- BOOK-LIBRARY хранит книги, метаданные, обложки, переводы, jobs и download flow;
- React-админка управляет импортом, переводами, провайдерами и безопасностью;
- публичная SvelteKit-витрина показывает живой каталог;
- Quartz показывает отобранный статический слой: подборки, карточки, заметки и mirrored covers.

Такое разделение спокойнее, чем попытка сделать один инструмент для всего. Quartz остаётся хорошим сайтом для текста и связей. BOOK-LIBRARY остаётся рабочей библиотечной системой.
